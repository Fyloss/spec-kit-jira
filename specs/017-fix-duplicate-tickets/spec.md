# Feature Specification: The Mirror Only Ever Mirrors a Specification, and Every Ticket Carries the Specification It Came From

**Feature Branch**: `worktree-fix+duplicate-tickets-2`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "Bug found while testing the extension on a consumer repository: during the
Spec Kit `after_plan` phase, when the reconcile command was invoked, the agent wrote new marker comments
into `plan.md` pointing at brand-new Jira tickets (one new specification-role ticket and one new
story-role ticket) instead of reusing and updating the ones already recorded in `spec.md`. A guard rail
must make this impossible, for that hook and for every other Spec Kit hook. We should additionally put a
label on these tickets stating that the ticket was generated by Spec Kit, carrying the reference of the
specification folder (example: `001-test-page`)."

## Context — the defect this feature closes

The mirror is fired by six lifecycle events, and all six fire the *same* reconcile procedure over the
*same* target: the active feature's `spec.md`. That is the whole design — one specification, one parent
ticket, one child per user story, recognised on every subsequent run through the marker lines the mirror
itself wrote into `spec.md`.

Nothing enforces it. The reconcile entry point accepts a specification file as an optional positional
argument and treats **whatever path it is handed** as a specification: it parses it, assigns durable
identifiers to every heading that looks like a user story, splices those markers into the file, and
creates a parent plus its children in Jira. Handed `plan.md` — the artifact the host command has just
produced when `after_plan` fires — it does all of that to `plan.md`. The file carries no markers, so
nothing is recognised; nothing is recognised, so everything is created.

That is exactly what happened on a consumer repository. The `after_plan` hook fired, the calling agent
named the artifact the host had just written instead of the feature's specification, and the run
produced a second specification-role ticket and a second story-role ticket in Jira, plus two marker
lines spliced into `plan.md` — a file the mirror is supposed to *read a summary from*, never write to.
Both duplicates are indistinguishable, in Jira, from the originals: same project, same issue types,
similar summaries, and an identity marker that says the bridge created them, because the bridge did.

Three properties of the system turn a single mistaken argument into that outcome:

- **Recognition is marker-driven and file-local.** A specification's tickets are found by reading the
  markers in the file being reconciled. A different file has different markers — here, none — so the
  recognition pass has nothing to recognise and the planning pass has no reason to do anything but
  create.
- **The guard rails that do exist all sit downstream of the target decision.** The dispatch guard, the
  routing validation, the schema validation, the lifecycle filter, and the privacy guard each protect a
  correct run from a bad *value*; not one of them asks whether the file being mirrored is a
  specification at all.
- **A ticket carries no evidence of which specification it belongs to.** The identity marker records
  that the bridge created the ticket, but it lives in an issue property that cannot be searched, and it
  names an opaque durable identifier rather than a folder a human can recognise. Nothing on the ticket,
  visible in Jira's own UI or findable by an ordinary search, says *this ticket mirrors
  `specs/001-test-page`*. So a duplicate is invisible until someone reads both descriptions side by
  side, and there is no second signal the mirror itself could have consulted before creating.

This feature closes all three. The mirror refuses any target that is not a feature specification, before
it reads a byte of configuration or touches the network — so the reported episode ends with zero tickets
and an untouched `plan.md`. The lifecycle procedure the agent follows is tightened so the target is
resolved from the active feature and never from the artifact the host command just produced. And every
ticket the mirror manages gains a provenance label naming its specification folder — the human-readable,
searchable evidence the system is missing today, which also gives the mirror a second, independent way
to notice that a specification's tickets already exist before it creates a single one.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A run aimed at anything but a specification refuses, before it can duplicate (Priority: P1)

A developer runs `/speckit.plan` on a bound repository. The `after_plan` hook fires the mirror, and the
calling agent — through a defect, a paraphrase, or an operator typing the path by hand — names
`plan.md` instead of the feature's `spec.md`. The mirror recognises immediately that the target is not a
feature specification and stops there: no configuration is read, no credentials are resolved, no request
reaches Jira, no identifier is assigned, and `plan.md` is left byte-for-byte as the host wrote it. The
developer sees one line naming the rejected file and the target that would have been correct, and
`/speckit.plan` completes normally as it always does.

**Why this priority**: This is the guard rail the defect calls for. Every other part of this feature
makes the damage visible or recoverable; this part makes it impossible. A duplicate created in Jira
costs a human a manual clean-up in two systems — the ticket and the marker line — and, unlike almost
everything else the bridge does, cannot be undone by re-running anything.

**Independent Test**: Can be fully tested with a feature folder holding a `spec.md` and a `plan.md`,
against a Jira double that fails the test if it receives any request at all: invoke the mirror with
`plan.md`, assert zero requests reached the double, assert `plan.md` is byte-identical to its
pre-run bytes, assert the run summary names the rejected-target cause, and assert the same result for
every one of the six lifecycle events and for a direct invocation.

**Acceptance Scenarios**:

1. **Given** a bound repository and a feature folder holding `spec.md` and `plan.md`, **When** the
   mirror is invoked with `plan.md`, **Then** the run performs zero Jira requests, creates zero
   tickets, modifies no file, and reports one named rejected-target cause.
2. **Given** the same repository, **When** the mirror is invoked with `tasks.md`, `research.md`,
   `data-model.md`, `quickstart.md`, a file under `contracts/`, or any other path whose file name is not
   `spec.md`, **Then** the outcome is identical to scenario 1.
3. **Given** a rejected target, **When** the run reports its cause, **Then** the message names the
   rejected path and, when the same folder holds one, names that folder's `spec.md` as the correct
   target, spelled exactly as it must be passed.
4. **Given** a rejected target, **When** the run ends, **Then** the rejected file carries no
   specification marker and no story marker written by this run — the refusal precedes every splice.
5. **Given** a run dispatched by any of the six `after_*` lifecycle events with a rejected target,
   **When** the mirror refuses, **Then** the host lifecycle command still completes successfully and the
   developer sees exactly one line.
6. **Given** a feature folder whose `spec.md` is the target, **When** the mirror runs, **Then** it
   behaves exactly as it does today — the guard changes nothing on the correct path.
7. **Given** the same corpus on both ports, **When** each is run, **Then** their outputs are
   byte-identical.

### User Story 2 - Every ticket the mirror manages names its specification folder (Priority: P1)

A tech lead opens the Jira board and sees, on every ticket the bridge produced, a label naming the
specification folder it mirrors — `speckit-001-test-page` on the parent and on each of its children. They
can search that label and get exactly that specification's tickets, and nothing else. When a stray
duplicate does exist — created before this release, or by a hand-run command — it stands out because it
is either unlabelled or labelled for a different specification.

**Why this priority**: Today a ticket carries no visible, searchable evidence of where it came from. That
absence is what made the reported duplicates hard to spot and impossible for the mirror itself to
notice. The label is also the prerequisite for User Story 4, and it is what the operator asked for
explicitly.

**Independent Test**: Can be fully tested against a Jira double: mirror a specification, assert every
created ticket's payload carries the provenance label for its folder; re-run unchanged and assert zero
writes; strip the label on the double and re-run, asserting exactly one update per ticket that restores
it and no other field changes.

**Acceptance Scenarios**:

1. **Given** a specification at `specs/001-test-page/spec.md` with two user stories, **When** the mirror
   creates its tickets, **Then** the parent and both children each carry the label
   `speckit-001-test-page`.
2. **Given** a project whose configuration already sends labels of its own, **When** the mirror creates
   a ticket, **Then** the payload carries both those labels and the provenance label, and the mirror
   never removes a label it did not add.
3. **Given** a specification whose tickets already exist and are recognised but predate this release,
   **When** the mirror runs, **Then** each such ticket is updated exactly once to add its provenance
   label, the update is counted and reported, and no other field of the ticket changes.
4. **Given** that same specification, **When** the mirror runs a second time with nothing changed,
   **Then** it reports zero created and zero updated — the label costs nothing on a settled mirror.
5. **Given** an operator who deleted the provenance label from a ticket by hand, **When** the mirror
   next runs, **Then** the label is restored without a warning and without touching anything else.
6. **Given** a project whose issue types do not accept labels, or a folder reference the tracker cannot
   hold as a label, **When** the mirror runs, **Then** every ticket is still created and updated exactly
   as it is today, and the run reports one named warning explaining that the provenance label could not
   be applied.
7. **Given** any run, **When** `--dry-run` is used, **Then** the reported action set carries the exact
   labels the real run would send.

### User Story 3 - The lifecycle procedure can only ever name the active feature's specification (Priority: P2)

An agent executing any of the six `after_*` hooks resolves the target the same way every time: it reads
the active feature directory and uses that directory's `spec.md`. It is told, in the procedure it
follows, that the artifact the host command has just produced — a plan, a task list, a research note, an
analysis report — is never the target, whatever the event is called. With no active feature the step
stays inert, exactly as today.

**Why this priority**: User Story 1 makes the mistake harmless; this makes it rare. The two are
independent: the bridge must refuse a bad target even if every agent behaves, and the procedure must be
unambiguous even though the bridge refuses. It is P2 only because, on its own, it prevents nothing that
User Story 1 does not already stop.

**Independent Test**: Can be fully tested by the existing agent-document contract tests: assert the
reconcile procedure states the single-target rule, names the artifacts that are never targets, and
carries the rejected-target cause in its message-discipline table.

**Acceptance Scenarios**:

1. **Given** the reconcile procedure document, **When** it is read, **Then** it states that the target
   is always the active feature's `spec.md` and that the artifact the host command just produced is
   never the target — stated once for all six events, not per event.
2. **Given** the same document, **When** its message-discipline table is read, **Then** the
   rejected-target refusal appears as its own named cause with the one line the agent is to report.
3. **Given** the same document, **When** its flag list is read, **Then** the optional positional is
   documented as accepting a feature specification file only, and its refusal behaviour is stated.
4. **Given** a repository with no active feature, **When** a lifecycle event fires, **Then** the step is
   inert and reports nothing — unchanged from today.

### User Story 4 - A specification whose tickets already exist is never mirrored twice (Priority: P3)

A specification's markers were lost — the file was regenerated from the template, the markers were
deleted, or the specification was copied into a new folder — and the mirror is about to create a full
set of tickets that already exist. Before creating anything, it looks for tickets already carrying that
specification's provenance label in the project the folder routes to. Finding some, it refuses to create
for that specification, names every key it found, and tells the operator how to bind them instead.

**Why this priority**: This is the second, independent guard rail — the one that catches a duplication
whose cause is not a mistaken target. It is P3 because it depends on User Story 2 having labelled the
estate first, and because a repository that has never lost a marker never reaches it.

**Independent Test**: Can be fully tested against a Jira double holding a labelled parent and child for
`speckit-001-test-page` and a specification file at that folder with its markers stripped: run the
mirror and assert zero creations, a named refusal cause listing both keys, and a message naming the
remedy.

**Acceptance Scenarios**:

1. **Given** a specification with no markers and a project already holding tickets labelled for that
   specification folder, **When** the mirror runs, **Then** it creates nothing for that specification,
   refuses with a named cause listing every ticket key it found, and names the remedy by a command
   that actually ships.
2. **Given** that refusal, **When** the run ends, **Then** the found tickets are untouched — not
   adopted, not edited, not relabelled, not transitioned.
3. **Given** a specification whose markers *do* bind it to those very tickets, **When** the mirror runs,
   **Then** the ordinary recognised path runs and nothing is refused — the check never fires on a
   healthy mirror.
4. **Given** a site where the search cannot be performed at all, **When** the mirror runs, **Then** it
   proceeds exactly as it does today with one named warning, never blocking the mirror on a guard it
   could not consult.
5. **Given** a specification whose folder holds no tickets under its label, **When** the mirror runs,
   **Then** creation proceeds normally with no extra output.

### Edge Cases

- **The damage already done.** A consumer repository already carrying marker lines in `plan.md` and two
  orphan tickets in Jira: the guard stops any further duplication, and reconciling the feature's
  `spec.md` reports a named warning listing every sibling artifact in the feature folder that carries a
  bridge marker line. The mirror never reads, rewrites, or deletes those files, and never touches the
  orphan tickets — the clean-up is the operator's, and the warning tells them where to look.
- **The target is a directory**, a path that does not exist, a symlink resolving to a `spec.md`, a
  relative path spelled `./specs/001-x/spec.md`, or a path carrying trailing whitespace.
- **A case-insensitive filesystem** offering `SPEC.MD` or `Spec.md` where the rule expects `spec.md`.
- **A specification file the host renamed**: a repository that does not call its specification `spec.md`
  is refused by the guard. The message names what was expected; supporting an alternative name is not
  part of this feature.
- **Two specification folders sharing a basename** in different parent directories resolve to the same
  provenance label. Within one `specs/` tree the basename is unique, so this only arises in a layout the
  bridge does not otherwise support.
- **A folder reference longer than the tracker's label limit**, or one carrying a character a label
  cannot hold: no label is sent, one named warning is reported, and every ticket is still mirrored.
- **A ticket adopted from a human author** through the single-ticket mention path: it is bridge-managed
  from adoption onward, so it is labelled like any other bound ticket — additively, with nothing the
  human wrote removed.
- **A ticket created by the feature ceremony** before its specification folder existed carries no label
  at creation; the first reconcile of that specification back-fills it.
- **A halted, flagged, or drifted ticket** whose content write is suppressed: the provenance label is
  part of that suppressed write, not an exception to it. An operator's manual hold is never bypassed to
  add a label.

## Requirements *(mandatory)*

### Functional Requirements

**The target guard (User Story 1)**

- **FR-001**: The mirror MUST refuse any target whose file name is not `spec.md`, and MUST perform that
  check before reading any configuration, resolving any credential, issuing any network request, and
  writing to any file.
- **FR-002**: A refused run MUST create zero tickets, issue zero requests of any kind, and leave every
  file on disk byte-identical to its pre-run state — in particular it MUST NOT splice a specification
  marker or a story marker into the rejected file.
- **FR-003**: The refusal MUST be reported as its own named, distinct cause, naming the rejected
  path — never phrased as a generic usage error and never as a missing-argument error. The
  prohibition is on the reported cause, not on the numeric exit code: the refusal reuses an existing
  code in the monotonic scheme (see Assumptions) and is distinguished by its message, which is fixed
  verbatim. Exit `1` is shared with the existing missing-or-unreadable-argument refusal, so the code
  narrows the cause to the usage class and the message names which of the two it is. Like every other
  pre-configuration refusal it returns before a run summary exists, so the message is the whole of the
  output.
- **FR-004**: When the rejected target's own folder holds a `spec.md`, the refusal message MUST name
  that file as the correct target, spelled exactly as it must be passed. The message MUST NOT spell
  out an entry-point invocation: the entry point differs per port, and FR-027 requires both ports to
  emit the same bytes.
- **FR-005**: The guard MUST behave identically however the run was dispatched — under any of the six
  `after_*` lifecycle events, or a direct invocation — and MUST NOT consult configuration to decide
  whether it applies. The single exception is an event the operator has explicitly disabled: that
  event stays silent and reports nothing, as it does today, because it performs no work and can
  create nothing. Feature 003's FR-020 governs that case and is not relaxed here.
- **FR-006**: A refusal MUST remain non-blocking for the host: the host lifecycle command completes
  successfully and the developer sees exactly one line, as with every other reported cause.
- **FR-007**: When reconciling a valid specification, the mirror MUST report a named warning listing
  every other **top-level** file of the same feature folder that carries a bridge marker line, and
  MUST NOT modify or delete those files. The scan does not recurse into subdirectories: every
  host-produced artifact a hook could plausibly hand the mirror sits at the top level, and the
  reported damage did. This warning MUST NOT block the run or change its exit code.
- **FR-008**: `--dry-run` MUST predict a refusal exactly as a real run performs it.

**The provenance label (User Story 2)**

- **FR-009**: Every ticket the mirror creates — the specification-role parent and every story-role
  child — MUST carry a provenance label naming the specification folder it mirrors.
- **FR-010**: The provenance label MUST be the fixed prefix `speckit-` followed by the
  specification's own recorded identifier — the value the mirror already validates for every
  specification, which for the folder `specs/001-test-page/` is `001-test-page` — giving
  `speckit-001-test-page`. That identifier is already a single whitespace-free token by
  construction, so the label needs no substitution rule of its own.
- **FR-011**: A recognised ticket that does not yet carry its provenance label MUST have it added, once,
  as part of that ticket's ordinary update, counted and reported like any other update.
- **FR-012**: The provenance label MUST be merged with every label the project's configuration already
  sends, and the mirror MUST NEVER remove or replace a label it did not add.
- **FR-013**: Once every managed ticket carries its provenance label, a subsequent unchanged run MUST
  report zero created and zero updated — the label MUST NOT become a source of churn.
- **FR-014**: When the routed project's issue types do not accept labels, or the folder reference cannot
  be expressed as a label, the mirror MUST mirror everything else exactly as it does today and report
  one named warning; it MUST NOT refuse the run and MUST NOT let the label cost a ticket its write.
- **FR-015**: The labels a run would send MUST appear in the reported action set, so that `--dry-run`
  and the real run agree on them exactly.
- **FR-016**: The specification-folder reference MUST travel from the engine as a neutral provenance
  value; the rendering of that value as a tracker label MUST exist only in the sink.
- **FR-017**: The provenance label MUST pass through the pre-write privacy scan like every other
  outbound value.
- **FR-018**: A ticket whose content write is suppressed — halted status, operator flag, or unresolved
  drift — MUST NOT be labelled either; the label follows the write, it is never an exception to a hold.

**The lifecycle procedure (User Story 3)**

- **FR-019**: The reconcile procedure document MUST state, once for all six `after_*` events, that the
  target is the active feature directory's `spec.md`, resolved from the recorded active feature.
- **FR-020**: The same document MUST state that the artifact the host command has just produced — a
  plan, a task list, a research note, a data model, a quickstart, a contract, an analysis report — is
  never the target of the mirror.
- **FR-021**: The document's message-discipline table MUST carry the rejected-target refusal as its own
  named cause, with the single line the agent reports for it, and its flag list MUST state that the
  optional positional accepts a feature specification file only.

**Duplicate detection before creation (User Story 4)**

- **FR-022**: Before creating any ticket for a specification, the mirror MUST look for tickets already
  carrying that specification's provenance label in the project the specification routes to.
- **FR-023**: When such tickets exist and the specification file holds no marker binding them, the
  mirror MUST create nothing for that specification, MUST refuse and report a named cause listing
  every key it found, and MUST name the remedy — the bridge command that binds an existing ticket to this
  specification — by a name that actually ships. Naming a command the operator does not have is a
  defect, not a remedy.
- **FR-024**: This check MUST be read-only: it MUST NOT adopt, edit, relabel, transition, or otherwise
  write to any ticket it finds.
- **FR-025**: When the search cannot be performed on the site at all, the run MUST proceed exactly as it
  does today with one named warning; a guard that cannot be consulted MUST NOT block the mirror.
- **FR-026**: The check MUST NOT fire for a specification whose markers already bind it to the tickets
  found — a healthy mirror sees no change in behaviour and no extra output.

**Both ports**

- **FR-027**: Every behaviour above MUST be implemented in both ports and produce byte-identical output,
  proven by the shared conformance corpus.

### Key Entities

- **Feature specification target**: the one file a mirror run may act on — a feature folder's `spec.md`.
  Every other artifact in that folder is an input the mirror may read (the plan summary) or ignore, never
  a target.
- **Provenance value**: the specification's recorded identifier — ordinarily its folder name, and
  always the value the mirror already validates for that specification — carried neutrally from the
  engine to the sink as the evidence of which specification a ticket mirrors.
- **Provenance label**: the sink's rendering of that value as a tracker label,
  `speckit-<identifier>`, visible in Jira's UI and findable by an ordinary search.
- **Stray marker report**: the list of files inside a feature folder, other than its `spec.md`, that
  carry a bridge marker line — reported, never touched.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Over a complete six-event lifecycle on one feature, the number of tickets in the tracker
  equals one parent plus one per user story, whichever artifact the calling agent names at each event —
  zero duplicates, in every combination.
- **SC-002**: 100% of runs whose target is not a feature specification end with zero tickets created,
  zero requests issued, and every file on disk byte-identical to its pre-run state.
- **SC-003**: Given a specification folder reference, an operator can list every ticket the mirror
  manages for that specification with one search, with no ticket from another specification in the
  result.
- **SC-004**: A second, unchanged run over an already-labelled specification reports zero created and
  zero updated.
- **SC-005**: 100% of the refusals and warnings introduced by this feature leave the host lifecycle
  command successful, with exactly one line reported to the developer.
- **SC-006**: A repository whose project cannot hold the label mirrors the same tickets with the same
  content as it does today, differing only by one named warning.
- **SC-007**: Both ports produce byte-identical output for every scenario introduced here, proven by the
  shared conformance corpus.
- **SC-008**: An operator whose repository was damaged by the reported defect learns of every stray
  marker file in the affected feature folder from a single ordinary run, without reading any file
  themselves.

## Assumptions

- The specification file name is exactly `spec.md`, as every Spec Kit template produces. A repository
  that renames it is refused by the guard rather than heuristically accommodated.
- The provenance label's prefix is the fixed literal `speckit-`. Making it configurable is not required
  by the reported defect and would add a key to the committable configuration for no demonstrated need.
- One label carries both facts the operator asked for — that the ticket was generated by Spec Kit, and
  which specification folder it belongs to. A second, generic label naming only the tool is not added.
- The provenance value is the specification's recorded identifier, which the mirror already
  validates as `NNN-lowercase-slug` before any write. A specification numbered in the host's
  timestamp style fails that validation today, before this feature is reached — the label inherits
  that existing constraint rather than adding one, and this feature does not lift it.
- A ticket adopted from a human author through the existing single-ticket mention path is bridge-managed
  from that point on, so it is labelled like any other bound ticket. The label is additive; nothing the
  human wrote is altered.
- The duplicate check of User Story 4 uses whatever ticket-search capability the site already grants the
  bridge's existing credentials. It requires no new permission, and a site that grants none falls back to
  today's behaviour under FR-025.
- The refusal exit code sits in the existing monotonic scheme rather than introducing a new one; which
  existing code it maps to is settled at planning time, and in every case the host command stays green.
  The code is `1` (usage), which is already claimed by the missing-argument refusal; the two are
  distinguished by their messages, not by the code.

## Out of Scope

- **Repairing damage a previous release caused.** Marker lines already spliced into a non-specification
  artifact, and tickets already duplicated in Jira, are reported (FR-007) and never touched. Removing
  them is the operator's decision, in their own tools.
- **Label-based adoption of an unmarked backlog** — the separate, opt-in second controlled exception of
  Principle I, specified elsewhere. Nothing here adopts, edits, or claims a ticket the bridge does not
  already manage.
- **A configurable label prefix**, an additional generic tool label, or any label the operator can
  template.
- **Mirroring `plan.md`, `tasks.md`, or any other artifact as tickets of their own.** The plan summary
  remains an input to the parent's description and nothing more.
- **Supporting a specification file under a name other than `spec.md`.**
