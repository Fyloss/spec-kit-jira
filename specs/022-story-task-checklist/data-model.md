# Phase 1 Data Model: A Story Carries Its Task List as a Checklist

**Feature**: 022-story-task-checklist | **Date**: 2026-08-09

Four entities. Two are new (§1, §3), one is an existing structure read in a new way (§2), and one is an
addition to an existing report (§4). Nothing in the neutral interchange document changes — see
[research.md](./research.md) §6 for why that is the design's central economy.

---

## 1. The task mirror mode

**What it is**: a per-project choice of how the task tier reaches Jira. Team-owned, committed,
hand-editable, ceremony-writable.

**Where it lives**: `.specify/jira/config.yml`, top-level, inside a managed region — the
`field_defaults` precedent (research §4).

```yaml
task_mirror:
  CONSUMER: checklist
  PLATFORM: subtask
```

| Field | Type | Rules |
| --- | --- | --- |
| key | string | A project key already declared in `projects[]`. An undeclared key is an error, exactly as `field_defaults.<PK>` is today (`lib/config.sh:691`). |
| value | enum | `subtask` or `checklist`. Nothing else. Case-sensitive. |

**Absence is meaningful and is not a synonym for either value.** Three states, not two:

| State | Meaning | Behaviour |
| --- | --- | --- |
| No `task_mirror` key at all, or no entry for this project | The team has not chosen | Feature 012's behaviour exactly: sub-tasks when a `task` role is declared, no task tier when it is not. Byte-for-byte identical output (FR-002). |
| `subtask` | Chosen explicitly | Same as above, but the ceremony stops asking, and FR-012 applies (say at config time when no sub-task type can be resolved). |
| `checklist` | Chosen explicitly | The task tier renders into story descriptions. No `task` role and no sub-task type is required (FR-005). |

**Validation** (`_cfg_schema_errors`, both ports), each producing `EXIT_CONFIG` with zero writes (FR-004):

1. `task_mirror` must be a mapping.
2. Each key must name a project declared in `projects[]`.
3. Each value must be `subtask` or `checklist` — the message names the setting, the project, the
   offending value and both accepted values.
4. `task_strategy` remains refused as retired (FR-006). This is an existing rule that must not regress,
   and it gets its own test.

**Resolution**: `config_task_mirror_for <project_key> <merged-cfg-json>` → `"subtask"`, `"checklist"` or
`""` (absent). Mirrors `config_field_defaults_for` (`lib/config.sh:845`) in name, placement and return
discipline.

## 2. The story checklist

**What it is**: the ordered, phase-grouped set of entries a story's ticket carries in checklist mode.

**It is not a new structure.** It is a *reading* of `stories[].tasks[]`, which feature 012 already puts in
the neutral document and `engine/interchange.sh` already validates. Every field the checklist needs is
present:

| Neutral field (existing) | Used for | FR |
| --- | --- | --- |
| `title` | the entry's text | FR-016 |
| `done` | the entry's completion state | FR-025 |
| `phase` | the group the entry sits under | FR-018 |
| `attribution.story_ordinal` | which story's checklist it belongs to — already resolved by the nesting | FR-014, FR-022 |
| document order | the entry order | FR-018 |

**Deliberately unused**, and this is a requirement rather than an omission (FR-019): `files`,
`depends_on`, `parallel`, `task_ref`, `local_id`, `description.blocks`. The first four are the per-task
detail the checklist trades away for volume. `task_ref` is excluded specifically by FR-017 — it is
regenerated by `/speckit-tasks` and would churn. `local_id` is excluded because a checklist entry is not
independently addressed (FR-031).

**Derived entry**, computed in the sink:

| Field | Derivation | Rules |
| --- | --- | --- |
| text | `title`, tokenised through the existing Markdown subset | Same renderer path as a sub-task description body, so both modes read identically (FR-016, FR-023). |
| state | `done` | `true` → complete, `false` → incomplete. |
| ordinal | position within the story's own task list, 0-based | Not the `T012` reference. Fixes the entry's order within its group; it reaches no rendered attribute, because the shipped nodes carry no identity (rendering contract §3). |
| group | `phase`, or none | Entries with no phase form a leading group with no heading (contract §2). |

**Cardinality**: exactly one checklist section per story that has at least one attributed task; **none at
all** for a story with zero (FR-021 — no empty section, no placeholder entry).

## 3. The checklist drift record

**What it is**: what the mirror last wrote, so that a difference on the ticket can be attributed to a
person rather than to `tasks.md` (FR-027).

**Where it lives**: the Jira identity entity property, beside the fields it already carries. Today's
stamp (`plan_apply.sh:352`):

```json
{ "origin": "bridge", "story": "<local_id>", "role": "story", "summary": "<last summary sent>" }
```

gains one field:

```json
{ "origin": "…", "story": "…", "role": "story", "summary": "…", "checklist": "<digest>" }
```

| Field | Type | Rules |
| --- | --- | --- |
| `checklist` | string, 40 hex characters | `git hash-object --no-filters` over the canonical JSON of the **normalised** checklist nodes (rendering contract §5). Present only on a story the mirror wrote a checklist to; absent otherwise, and absence means "no record yet", never "empty checklist". |

**Compatibility**: an absent `checklist` field on a ticket written by an earlier release is the "no record
yet" row of the decision table — write, no warning. No migration, no backfill, and a ticket from before
this feature is not warned about on its first reconcile.

**The digest is never the comparison for churn.** Zero churn is decided by
`plan_managed_description_status` over the managed nodes (research §2). The digest answers a different
question — *did a human touch it* — and the two must not be conflated.

## 4. The run summary's checklist counts

Added to the reconcile summary, distinct from the specification, story and sub-task tallies (FR-036):

| Count | Increments when |
| --- | --- |
| `checklists.created` | A story receives a checklist section it did not have. |
| `checklists.updated` | A story's existing checklist section changes. |
| `checklists.unchanged` | A story's checklist is byte-identical after normalisation — the zero-churn case. |
| `entries.completed` | An entry moves from incomplete to complete in this run. Counted per entry, across stories. |

Plus three named report lines, which are messages rather than counts:

- **Unmirrored tasks** — one line per unattributed task, by task identifier, with the reason (FR-022).
  Reuses the vocabulary sub-task mode already emits, so the two modes report the same fact the same way.
- **Mode switch** — one line naming the stories, the count of sub-tasks the mirror no longer maintains,
  and the copy-pasteable `issue in (…)` query (FR-034, research §6).
- **Declared-but-unused `task` role** — one line, once, when checklist mode is active and a `task` role
  is also declared (spec Edge Cases: "the mode wins… so nobody concludes both are happening"). This
  replaces feature 012's FR-012 status line in this mode rather than adding a second one.

**Dry run** shows all four counts and all three report lines, plus each planned checklist's entries and
their state (FR-037), and writes nothing.

## Entity relationships

```text
config.yml
  └── task_mirror: { <PROJECT_KEY>: subtask | checklist }        (§1, FR-001)
          │ resolved per run, per project
          ▼
      plan context .task_mirror
          │
          ├── "subtask"   → plan_writes_tasks            (unchanged, feature 012)
          │                 + task_marker assignment into tasks.md
          │
          └── "checklist" → _adf_checklist_nodes         (§2, FR-014…FR-018)
                              │  appended to the story's managed nodes
                              ▼
                            story description  ── compared ──▶ zero churn (research §2)
                              │
                              └── digest ──▶ identity property .checklist   (§3, FR-027)

tasks.md
  └── task markers (durable identifiers)
        ├── written only in subtask mode                 (FR-031)
        └── read in checklist mode as switch evidence    (§4, FR-034)
```
