## T003 — project-keyed fault path matching

`tests/conformance/mock-jira/curl-shim.sh:361-366` (mirrored in
`mock-server.ps1:217`) computes `fault_path` as follows:
- For `POST /rest/api/3/issue`, `fault_path` is rewritten to
  `/<projectKey>` read from the request body's `fields.project.key` — the
  fault therefore targets exactly that create, regardless of the raw URL.
- For every other request (GET createmeta, GET issue-by-key reads, property
  GETs used by the identity/recognition guard, etc.), `fault_path` is left as
  the raw request path. Because the match pattern is `/<key>(/|-|$)`, any read
  whose path contains the project key as a path segment — e.g.
  `/rest/api/3/issue/PM-1` or `/rest/api/3/issue/PM-1/properties/...` — is
  ALSO faulted by a fault configured for project `PM`, since `PM-1` begins
  with `PM-`.

Consequence for T029 (and for `test_plan_apply_outcome.bats` /
`PlanApply.Outcome.Tests.ps1`, which use project-keyed faults on synthetic
`AAA`/`BBB` projects to distinguish parent- vs story-rejection): those tests
only ever issue `POST` creates against the faulted project, never a
follow-up `GET` against an already-created `AAA-N`/`BBB-N` key, so no
collateral faulting occurs in practice. A scenario that DID need to read back
an issue in a project under an active fault (e.g. a recognition/backfill read)
would be collaterally faulted by this same rule — worth flagging to a future
scenario author, but no such scenario exists in this feature's corpus.
